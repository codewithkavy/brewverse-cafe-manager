## Priorities

1. **Tenant security foundation** — *Firestore least-privilege rules pass 9 emulator tests; isolated Storage rules pass 4 tests, including denial for malformed active roles. AuthGate has opt-in tenant mode with membership selection/onboarding; Home, Inventory, Billing, and CafeService accept a selected café ID. Tenant mode scopes reads and routes stock, recipe, and checkout mutations through trusted callables. Inventory mutation controls are hidden from staff while owner/manager controls remain; tenant managers can upload café-scoped inventory photos. Owners/managers have a café-scoped team screen backed by a role-checked, paginated member-list callable; additions require an existing account email and do not send invitations. Tenant mode is disabled by default and blocked from live Firebase unless separately enabled; emulator mode uses project ID `brewverse-security-tests`. Trusted backend has 15 membership/inventory workflow tests, 7 migration/preflight tests covering recipe and bill reference integrity plus the read-only CLI, and 3 authenticated callable integration tests covering checkout, role limits, team listing across two cursor pages (204 members with no gaps), malformed cursor rejection, and revoked access. An offline ownership preflight validates explicit mappings and cross-café references for supplied exports; real ownership verification, backup, migration rehearsal, staging validation of the new index manifest, email invitations, live rollout, photo upload on device, and device verification remain.* Keep rules test-only until ownership, backup, migration, and rollout are verified.
2. **Inventory and movement correctness** — *single-cafe Flutter behavior and isolated trusted handlers cover opening stock, stock additions, checkout deductions, and atomic movement records. Flutter Firestore-backed tests and backend emulator tests cover those paths. Editing item details preserves live quantity. Tenant-mode reads and writes route through the scoped service/callable path; older movement records still fall back to item IDs where names/units are missing.* Production migration and live rules remain unverified.
3. **Recipe management** — *the finished-product editor persists recipes. Tenant-mode recipe reads are café scoped, and saves use a trusted handler that validates same-café product and stock references; backend emulator tests cover cross-café rejection.*
4. **Billing and checkout integrity** — *legacy Flutter and isolated trusted checkout use transactions and duplicate checkout IDs. Flutter uses structured request keys to avoid delimiter collisions and verifies saved bill contents before accepting old-format retries. Flutter service tests cover key collisions, old retries, duplicate checkout, and insufficient-stock rollback; backend emulator tests cover staff checkout, retry, insufficient-stock rollback, and ID reuse with changed order. Tenant mode routes checkout to the trusted handler, with callable integration coverage. Production concurrency and live-device behavior remain unverified.* Keep stock changes within the transaction.
5. **Receipt output and Bluetooth thermal printing** — *BLE scan/select/connect/print flow and Android BLE permissions are implemented after successful checkout. Receipt generation now validates each saved line amount and the bill total against the saved item quantities/prices before printing. Build is verified; printer discovery, receipt output, and runtime permission behavior still need a real Android device and BLE thermal printer.* Add reconnect/settings behavior only after hardware testing.
6. **Sales insights** — *isolated trusted callable and tenant-mode dashboard panel implemented.* It calculates completed-bill totals and best sellers from saved bill records, scopes reads by active café membership, uses a bounded date range, and has emulator coverage for void bills, other cafés, and end-exclusive dates. The dashboard shows actual saved revenue, order counts, items, and best sellers, with explicit refresh and an empty-period state. Composite index definitions are now linked from the local Firebase CLI config; staging index validation and live-device verification remain.
7. **Customer loyalty** — *trusted per-café policy settings, owner UI, phone lookup, checkout earn/redemption, expiring point buckets, idempotent transaction ledger, partial refunds, and void reversal are implemented.* Defaults are 4 points per ₹100, ₹1 per point, 5 bonus points at ₹500, 10 at ₹1,000 (highest tier only), and 12-month expiry. Owners can edit earning, bonus, expiry, redemption cap, and refund reversal options. Server callables validate membership, policy and checkout/refund operations; retry IDs prevent duplicate postings. Flutter suite and isolated backend tests cover key flows; callable emulator tests previously passed. Refunds do not restock consumed recipe ingredients. Preserve existing data; no production rules deployment without approval.
8. **Release verification** — *latest recorded Flutter suite: 80 tests; analyzer: no issues; Android debug APK build: passed; isolated backend suite: 33 tests; 9 Firestore authorization emulator tests and 4 Storage authorization emulator tests passed in earlier recorded runs; 4 callable integration emulator tests passed in an earlier run.* A GitHub Actions workflow defines repeatable checks; its first hosted run is pending. The Storage Emulator’s Java rules runtime emits a NullPointerException during shutdown despite a successful test exit; this environment warning remains. The build warns that the Cloud Functions plugin applies Kotlin Gradle Plugin; a future Flutter release may require plugin migration. Current `flutter devices` reports Windows, Chrome, and Edge only; no Android phone is detected. Runtime checkout/printing and device workflows are unverified. Keep rules test-only until ownership, backup, migration, indexes, and rollout are verified.

- Emerald theme/dashboard UI work is present in the working tree and will be preserved. Continue the active UI-fidelity scope above before resuming backend roadmap work.
